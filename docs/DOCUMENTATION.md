# TppGekko documentation

Reference for continuing the work. Addresses without a prefix are in Metal Gear Survive `mgv.exe` (image base 0x140000000). Addresses marked "TPP" are in MGSV:TPP 1.0.15.4. The two images share the address range but are different builds: an address never carries over without its own signature check.

Contents: 1 Goal and scope, 2 What is needed from each game, 3 How the port works, 4 What is substituted, 5 Findings, 6 Lua API and debug menu, 7 Build and test, 8 Open work.

## 1. Goal

The goal is the Survive gekko as a spawnable, animated, AI-driven enemy in TPP. The Survive brain runs inside TPP: Survive's own code makes the decisions, TPP supplies the services it needs. A call the lifted code makes into the engine is answered by one of three things: a lifted Survive function, a TPP function (an identical twin or a forwarder to the TPP object), or a host answer listed in section 4.

Currently only spawns one gekko at a time (the DLL drives id 0), checkpoint spawn and despawn not wired in (needs redeploying to despawn it, broken).
## 2. What is needed from each game

### 2.1 Metal Gear Survive (mgv.exe)

mgv.exe is read at build time. The lifted module is generated from the locally installed copy and is never committed.

Code that is lifted and run:
- AI state machine `0x140f8d3f0`, its 13 state handlers (table `0x143086260`, initialiser `0x141f7dbd0`), the state chooser `0x140f8d510` and the melee chooser `0x140f911f0`.
- Movement brain `0x140fa46d0`, a path follower with its own mode machine, and its order initialiser `0x140fa6910`.
- Locomotion component: handler table `0x143086190` (idle `0x140f898c0`, stop `0x140f89af0`, walk `0x140f89ec0`, turn `0x140f89c10`), executor `0x140f88720`, base tick `0x141092020`, arrival test `0x140f88780`.
- 31 action handlers (table of 32), the Realized dispatch `0x140f93d30`, the event mapper `0x140f94cb0` and the plugin event path `0x140f81220`.
- Path tracker query `0x140f7f7f0`.
- Observer (factory `0x140f72e40`, setup `0x140f74080`).
- Push targets: creation `0x140f80e30`, per-frame placement `0x140f82280`, plugin frame function `0x140f78a90` (execution kinds 0, 3, 5).
- Gecko LifeController and damage handler (setup `0x140f91ab0`), fed by the parameter block.
- Nav controller `NavigationController2Impl` (creator `0x141408ca0`), optional, see 3.4.

Data read from Survive:
- Animation table: 79 slots at `.data` `0x142a237d0`. An entry is `0xfc5` shifted left by 52, ORed with the gani hash from `Gecko_layers.mtar`.
- Event keys in the `.enchnk` of each gani.
- Gecko parameter struct layout and loader (`SsdGeckoParameter`, loader `0x140b983f0`, see 5.6).
- Damage tables `SsdDamageParameter` (Blowfish ECB big-endian plus zlib, key at `0x1421f88c0`).

Key structures:
- Request mailbox `0x140e96b60` (lifted, a method of the ActionController, 5.10). Request record 0xc0 bytes: +0x10 target descriptor, +0x20 action id, +0x24 flag byte, +0x90 position, +0xb8 order bits (bits 3 to 5 are the category: 0 plain action, 1 direct position order, 2 position order through the path), +0xb9 kind (4 action request, 1 move order). The mailbox copies the request into the unit's record at +0x20 and sets 0x200 in the record flags. The ActionController update commits it into the request array entry at `[[H+0x1c8] + 8]` plus id times 0xc0: word +0xae serial, byte +0xb6 kind (4 action, 1 move), word +0xb4 low two bits the order type (0 none, 1 path, 2 position) and bit 4 set when the consumer has taken it. Records at `[[H+0x1c8] + 0x10]` plus id times 0x1d0: word +0x1c4 flags (0x02 path pending, 0x08 accepted, 0x10 issued, 0x20 finished, 0x200 new request; the AI states test 0x20), +0x1b8 path handle, +0x200 controller, +0x228 id, +0x29c action, +0x29d pending action, +0x288 event flags. The low 3 bits of the target's fourth dword are a type (1 is a plain position, `0x140f7f240`).
- Handler `this` (H): +0x1a0 NPC service, +0x1b8 unit object (+8 table of unit entries of 0x60 each, +0x18 float array, +0x20 stride, +0x24 first id), +0x1d8 records (0x2c0 each), +0x228 first id. Unit entry: +0x20 animation controller, +0x38 float scales.
- NPC service (svc): +0x48 pose object (+0x20 16-byte pose entries per id: x y z yaw; +0x38 frame time array per id; +0x48 scale 1.0), +0x60 nav service, +0x68 owner lookup, +0x70 target provider (target vec4 at +0x20, id at +0x30, strength at +0x34), +0x78 route end object, +0x80 controller, +0xf8 state table (+8 entries of 0x28, +0x10 count, vtable +0x10 SetState), +0x108 event bus.
- AI state machine `0x140f8d3f0(S+0x20, id, ctx)`: records of 0x80 at `[S+0x1d8]`; state byte +0x7c, timer +0x74. The state is chosen from bit flags of the NPC state table entries. NPC state entry: 0x130 bytes per NPC; the tracker query reads bits 8 and 9 of dword +0x110.
- Order record read by the movement brain: +0xb0 route id (StrCode32, `0xbf169f98` means none), +0xac generation, +0xb4 vertex, +0xb8 mode. Mode machine: 0 no path, 1 path requested, 3 follow, 2 turn, 8, 9, 10 requests of actions 30 and 31.
- Locomotion instance record: +0xc state, +0xe requested, +0xf force; record +0x38 state flags (bits 1 and 2 switch the arrival test on); +0xb4 order type (1 path, 2 position).
- SsdNpc object: 0x428 bytes from factory `0x141073500`, class vtable `0x1422d2900`, interface `0xb567a90fe2c5` at object +0x28. NPC type database: global `0x142f9cfc0` (getter `0x140b6a730`, made by `0x140b6ab50`); gecko is id 13, npc type `0xbf304b9d`, class component `0xdc11dba59fbb` (SsdGecko).

### 2.2 MGSV:TPP (1.0.15.4)

The port calls these engine services and objects.

- Game object: type index 100, `TppGekko`, registered with `fox::gm::RegisterGameObjectFactory`. Created with `fox::gm::CreateGameObject {100, count, count}`. Pause comes from the engine's parallel execution context (see 5.8).
- Animation: the TPP full `AnimationController`. Survive's gekko also uses the full controller (Survive create `0x140bc1a20` equals TPP `0x140af0790`). Survive controller slots are forwarded to the identical TPP slots by `GekkoCtrlFwd.asm`. The motion finished query, Survive slot `0x2f8` (95), is TPP slot 87, identical code. A clip is played with a `TppMotionDesc` on layer slot 58, as Survive's controller slot `0x1f0` does.
- CharaControl and `VelocityControlAction`: pose, root motion, the CharaControl's own turn target (`SetTurn`), ground contact. `CharaControl::Create` with flag bit 2 and no owner faults; a game object is required.
- Motion output (steering inputs): TPP object `[[unit+0x60]]+0x10` (Survive slots `0x3d0` and `0x3d8` equal TPP slot 112). It holds the unit position at +0x20 and rotation at +0x60.
- Geo line check: `Geo::CollisionLineCheck` at TPP `0x141b9b130`. Survive's geo service has the same layout, constructor body and CharaControl filter `0x1000000000020`.
- Target service pool: PUSH_SLIDE targets are created in TPP's pool through a checked proxy. The player's `DefensePushSlideCallback` then slides the player away. The target service addresses are in `GekkoPush.cpp` and are checked on first use.
- Hit targets: the gekko's hit-target objects are TPP objects. They have a callback interface at object +0x30, installed by `GekkoHit`.
- Routes: `RouteSystemImpl` (TPP instance at `0x142baf2a8`, vtable `0x1421872a0`; `RouteGroupImpl` vtable `0x142187500`). It is the same class as Survive's; `GetRoute` and all 14 `RouteGroupImpl` slots have the same bodies.
- Nav: `NavigationSystem` and `Pathfinder` behind slot-order proxies. Survive slot k equals TPP k for 0 to 5, Survive 6 has no TPP counterpart, Survive 7 to 14 equal TPP 6 to 13. Path layout: `Path2Impl` points at +8 (16 bytes each, both builds), segments at +0x10 (Survive stride 0x30, flag dword +0x28; TPP stride 0x40, flag dword +0x30), count at Survive +0x28 and TPP +0x20. Survive's `Reserve` (`0x141bfb080`) also keeps a byte array at +0x18 and a u16 array at +0x20; TPP's (`0x141cd0660`) keeps a byte array at +0x18. For P (T+0x98): Survive `Initialize` calls slot `0xe8` of `[P+0x110]`, the TPP twin calls slot `0x90` of `[P+0x100]` (a type test, `0xc382` in both).
- Sahelan2 `RealizedSahelan2Impl::Execute` (TPP `0x140b4db20`) is the model for the per-frame structure.
- Infinite Heaven supplies the Lua side: the library is loaded from an IH module, and spawn, target and route calls come from Lua.

Twin evidence is regenerated with `tools/ctrl_slot_map.py`, `verify_twins.py` and `verify_ctrl_slots.py` against both exes. Ambiguous slots are reported and decided by hand.

## 3. How the port works

### 3.1 The lifter

`tools/lift/lift.py` is a static x64 to C++ recompiler. Every function becomes `void L_addr(Cpu& c)` over `c.r[16]` and `c.x[16]` (`__m128`). Flags are locals, so the compiler removes dead flag code. A private emulated stack keeps `[rsp+x]` frames exact; lifted calls push a fake return slot and `ret` pops it.
- Extent: the function's `.pdata` chunk, extended through chunks it falls into; leaf functions without unwind info are found by a linear scan. Only instructions reachable from the entry are lifted.
- Jump tables become switch statements; `jmp reg` through a pointer table becomes a tail call. Jump tables whose load reads the image base are recognised without executing the load.
- Calls go to a lifted function (direct), to a TPP twin (`lift_native_call` thunk: rcx rdx r8 r9, xmm0 to 3, 8 stack qwords), or through a pointer (`call_ptr`: tokens go to lifted code, anything else is native). Every call from lifted code into 0x140000000 to 0x150000000 passes `lift::g_native_gate`: it is refused and logged once unless `AllowNative` listed it.
- Data: referenced bytes are embedded as windows; qwords that point at code entries become tokens (token = `kTokenBase` plus VA). Zero windows reserve `.bss` objects.
- Instruction set: integer ALU with exact flags, shifts, rotates, imul (one-, two- and three-operand, 32 and 64 bit), mul, div, bit ops, string ops, cmov, setcc, push, pop and the SSE and SSE2 forms in the gekko code (121 mnemonics).
- `--pc` keeps a ring of the last lifted pcs (`LIFT_PC_TRACE`) so a fault prints the Survive instruction.

`tools/lift/lift_gekko.py` is the one place that lists the lift. `build_gekko.bat` runs it and relifts when `lift.py` or `lift_gekko.py` is newer than the module.
- ROOTS: the table initialisers (`0x141f7e070` action table, `0x141f7dbd0` AI state table, `0x141f7de50` second layer, `0x141f7d660` locomotion table), AI state 0 enter `0x140f8d8d0`, the shared empty stub `0x1402ba870`, the NPC factory `0x141073500` and its neighbours, the life class, generic DamageHandler and damage calculator creators (`0x141040790`, `0x141087040`, `0x140f51ef0`), the observer factory `0x140f72e40`, the singletons `0x141988fa0` and `0x141989050`, the locomotion base tick `0x141092020`, the path tracker query `0x140f7f7f0`, the plugin-frame helpers, and the nav controller roots (creator `0x141408ca0`, helpers `0x141408a60` and `0x14137e370`).
- VTABLES (29 vtables): classes whose virtual functions are all roots: the life class (`0x1422c8c80`, `0x1422c8cb0`), the generic DamageHandler (`0x1422d4c00`, `0x1422d4c30`), the damage calculator (`0x1422a5740`, `0x1422a5770`), the LifeController (`0x1422afe38`, `0x1422afe70`, `0x1422afdc0`) and the typed DamageHandler (`0x1422af448`, `0x1422af480`, `0x1422af4e8`) (the leaf virtuals such as the QI functions have no unwind info, so `--all-in` misses them: the first run refused `0x140f91a40`), the SsdNpc base class (`0x1422d2900`, `0x1422d2040`), the gekko Observer (`0x1422ad070`, `0x1422ace60`, `0x1422ace28`), the shared-object pool (`0x1423d8cb0`) with the target object classes it builds, and the nav controller classes with the Path2Impl path class. A vtable is data, so direct calls never reach its entries.
- `--all-in 0x140f60000 0x140fb0000`: everything in the gekko module range is lifted.
- FOLLOW (23 ranges): direct callees inside these ranges are lifted too: the life class `0x141040000` to `0x141043000`, the generic DamageHandler `0x141086000` to `0x141089800`, the shared damage code `0x140eaf000` to `0x140eb1000`, the damage calculator `0x140f50000` to `0x140f53800`, the response handler base `0x141015000` to `0x141016000`, the controller and effect code `0x140e7c000` to `0x140e83000`, the pool slot functions `0x141b18f00`, the component base class state machine `0x141091f00` to `0x141092600`, the NPC factory area `0x141070000` to `0x141082000`, the class constructors `0x141abb000` and `0x141ad5e00`, engine helpers that work on Survive-owned objects (`0x141af7000`, `0x140034000`), the nav controller `0x141408000` to `0x14140b000` and Path2Impl `0x141bf1000` to `0x141bfc000`. Engine helpers that touch Survive objects are lifted and not twinned, because the TPP twin walks TPP globals.
- `--resolver port_kit`: `tools/port_kit.py` decides which Survive callee has a TPP twin by prologue shape; `KNOWN_TWINS` holds the ambiguous ones decided by hand. Prologue shape alone is not enough: the TPP "twin" of the manager getter `0x141989050` (`0x140bff050`) is a different function.

Adding a root: put the address in ROOTS (a function nothing calls directly), VTABLES (a class whose virtual functions are all roots), or widen a FOLLOW range. Survive-only callees with no TPP twin print "survive-only no exact twin" in `build/gekko/lift.log`: lift them with a wider FOLLOW or answer them in the host.

Adding an environment hook (a Survive function replaced by a host function):
1. Declare `void env_name(lift::Cpu& c)` in `src/GekkoHook/lift_env.h` with a one-line comment (address, arguments in rcx rdx r8 r9, return in rax).
2. Implement it in `GekkoWorld.cpp` (read `c.r[RCX]` and so on, write `c.r[RAX]`). Headless tests link the same file.
3. Add `0xADDR=env_name` (or `0xADDR=nop`) to ENV in `lift_gekko.py` with a comment on where it was found.
4. Run `build_gekko.bat relift` or `run_world_test.py --relift`. A changed root or hook list is not picked up otherwise.
5. Every new TPP address needs a prologue signature in `GekkoSigs.h` (`tools/make_gekko_sigs.py`) or a checked twin entry.

### 3.2 Host shim

`GekkoWorld` (linked into the DLL and into the headless tests) builds the structures the lifted code reads: the NPC service, the record store, the order record, the locomotion records, the creation context and the hub. It answers the services that are not lifted (section 4), and provides the forwarders and the steering access. `CallAddr` runs a lifted function by address; `Begin` runs the Observer setup, which creates Survive's ActionController; `Request` builds a request the way an AI state does and sends it through Survive's own mailbox; `ActionUpdate` runs the ActionController update; `InitInstance`, `Dispatch`, `FireEvent` and `Run` drive the action and event paths; `MoveStep` runs the locomotion's move step; `TakeSteer` returns the heading the locomotion asked for; `AllowNative` lets a checked TPP function through the native gate.

### 3.3 TPP side (`src/GekkoHook`)

- `dllmain.cpp`: installs a first-chance exception logger so a crash leaves its address in `Gekko.log`. All work starts from `luaopen_Gekko`.
- `GekkoType`: registers the game object factory (false if a signature check fails or the slot is taken), creates and activates the object, places it, destroys it. Instance 0 has game object id 51200 (`kTypeIndex` shifted by 9). `AllocResources` finds the gekko parts and mtar files and spawns the gekko.
- `GekkoFull`: creates the full controller from the gekko's `AnimationControllerDesc`, adds the mtar, warps the CharaControl, plays clips, runs the TPP controller stages for the unit, returns feet position and yaw, sets the CharaControl's turn target from the brain's heading request (`SetTurn`, 4.8), keeps `SetYaw` as a one-shot manual heading, and returns run-frame seconds (`ConsumeRunTime`, 0 while paused).
- `GekkoAi`: takes pose and target in, steering out, and makes no decisions. It also starts and stops the brain, holds the last target, and starts a route walk (`Route`). Once per frame, before the brain, it feeds the queued TPP hits to `GekkoLife` (first damage byte of each record, hits on objects beyond the 21 hit spheres ignored) and runs the life update; when the Dead event has fired it stops the route loop, the push targets and the brain, turns the hit filter off and freezes the pose (`OnDeath`, 5.11).
- `GekkoBrain`: owns the per-frame call order of the lifted code (3.5), the line check hook into TPP geo (`OnLineCheck` aligns the buffers and ORs flag 0x700), and the melee request. With a spawn sequence the AI runs its own fall, stunned and get-up states (about 20 s); otherwise it starts at state 12.
- `GekkoPush`: creates the three PUSH_SLIDE targets with Survive's `0x140f80e30` against TPP's target service, places them each frame (`0x140f82280`), and runs the plugin frame function `0x140f78a90` for kinds 0, 3 and 5.
- `GekkoHit`: sets the callback interface on every hit-target object of the gekko and queues received hits (part index, damage bytes, flags, position, distance; newest 64 kept). `SetEnabled(false)` makes the hit filter refuse every hit, so bullets pass through a dead gekko.
- `GekkoLife`: builds the life and damage components over the host NPC service with Survive's own creators and Setup functions (section 4.6), feeds a TPP hit into them (`Hit`), runs the life update (`Update`), reads the state (`Read`) and reports the Dead event. Linked into the DLL and the headless tests.
- `GekkoRoute`: finds TPP's `RouteSystemImpl` instance, checks signatures and vtables, and hands a route to the movement brain.
- `GekkoNavProxy`: Survive-order proxies over TPP's `NavigationSystem` and `Pathfinder`, and the conversion of a TPP path to a Survive path (`ConvertPath`). `FillScope` fills the scope table the nav controller reads.
- `GekkoParam`: writes the Gecko parameter block (`GekkoParamBlock.h`) into the `SsdGeckoParameter` struct (5.7).
- `GekkoLegIk`: the leg fit animation plugin (5.12), switch `Gekko.LegIk`.
- `GekkoDebug`: the debug calls that drive single lifted parts (section 6).
- `GekkoLua`: the Lua library `Gekko`, loaded from Infinite Heaven with `package.loadlib(dll, "luaopen_Gekko")`.
- `GekkoLog`: `Gekko.log` (append, flush per line) and `ResolveGameAddress`.
- `GekkoSigCheck.h` runs one prologue check per signature in `GekkoSigs.h` at load. `GekkoGround.h` gives the ground height under a point through `fox::geo::CollisionLineCheck`. `GekkoFiles.h` and `GekkoBlocks.h` are debug views of the engine file table and fox block groups. `GekkoDriver.h` is the older spawn driver. `GekkoTargetProbe.h` and `GekkoPushProbe.h` are probes.
- Generated tables: `GekkoSigs.h` (build time, from the installed TPP exe), `GekkoParamBlock.h` (committed, 86 entries), `GekkoCtrlSlots.h` and `GekkoCtrlFwd.asm` (`tools/gen_ctrl_fwd.py`: Survive controller slot to the identical TPP slot), `GekkoTable.h` and `GekkoEvents.h` (clip table and clip events).
- `ProjectFolder/GekkoPort/GameDir/mod/modules` holds the Infinite Heaven modules `InfGekkoSpawn.lua` (spawn, brain, target, debug menu) and `InfGekkoRoutes.lua` (route follow).

### 3.4 Nav controller (optional)

With `DebugNavController(1)` set before the brain starts, `GekkoNavProxy` builds Survive-order proxies over TPP's `NavigationSystem` (S) and `Pathfinder` (B), and Survive's `NavigationController2Impl` is lifted and started as `[svc+0x60]` in place of the straight-line stand-in (4.2). It is on by default (without it the path is the straight two point stand-in of 4.2 and nothing is avoided; the Lua option `gekkoDebugNavCtl` and `DebugNavController` switch it). The log of 06/10 22:00 ran with it on.
- Proxies: Survive's `NavigationSystem` slot k is TPP slot k for k 0 to 5 and TPP slot k-1 for k 7 to 14; Survive slot 6 has no TPP counterpart and logs if called. B slots 0 to 5 map one to one. After each `ReceiveResult` the proxy runs `SyncEntry`, which copies the real table entry (state bytes and the converted path) into the Survive-layout table the controller reads.
- Path conversion: Survive's `Path2Impl` has points at +8 (16 bytes each, as in TPP), segments at +0x10 with stride 0x30 and flag dword at +0x28 (TPP stride 0x40, flag dword +0x30), and the count at +0x28 (TPP +0x20). `ConvertPath` builds the Survive copy with Survive's own constructor `0x141bf1e80`.
- Scope table: the scope table T is TPP's (from the accessor `0x140bff050`, prologue checked first) and agrees with Survive's at +0x98 (P) and +0xa0 (S). `FillScope` fills it for the controller.
- Controller creation: creator `0x141408ca0` and `Initialize` `0x141409320` (primary slot 1) run with the descriptor Survive's own quark creators pass: +8 key `0xb8a0bf169f98`, +0x10 key `0x62bcc8f4fcb6`, +0x18 u16, +0x1c float 9999.0. The gekko's own creator is not identified. `Initialize` builds a pathfinder descriptor in which desc+8 is the world name (`0xb8a0bf169f98`, the default world) and desc+0x10 is the key of the path optimizer executor; TPP's `Soldier2` controller passes `0x5b95c98dc68d` there.
- Per frame: `GekkoWorld::NavUpdate` feeds the unit position through interface slot 24 (`0x14140a700`) and the navigator radius, then calls `Update` (slot 15, `0x141409f10`). `NavDiag` and `NavProxy::Diag` log changes of the order record, the controller record and the pathfinder entry to `Gekko.log` (`[navctl]`, `[navB]`, capped).

### 3.5 Per frame execution order

- `ExecuteSerially` calls `GekkoAi::Update(dt)`. dt is `GekkoFull::ConsumeRunTime()`, 0 while the engine skips the unit (pause).
- `ExecuteInParallel` calls `GekkoFull::Execute(ctx)`: the TPP controller stages in Sahelan order (`ActMotionStart`, `ActMotion`, `CharaControl2`, `PutMotion`). If they ran, `GekkoBrain::ControllerRan()` tells the brain that a motion requested earlier is now applied.
- `GekkoAi::Update` first runs the life frame (hits in, life update, death, see 3.3), then reads the pose (feet xyz, yaw of the CharaControl), calls `GekkoBrain::Frame`, takes the steering request (shadow of the motion output fields, 4.8) and hands it to the CharaControl's turn target (`GekkoFull::SetTurn`, set or cleared every frame), then runs `GekkoPush::Update` and `GekkoPush::RunKind(0)`.
- `GekkoBrain::Frame` order (producers before consumers, because the host component order is not mapped): SetDt, SetPose, SetTarget; AI state machine `0x140f8d3f0`; movement brain `0x140fa46d0`; ActionController update `0x140e7a0f0`; locomotion tick `0x141092020` kind 1; Realized dispatch `0x140f93d30` kind 1; locomotion ticks kind 3 and 5; locomotion move step (`0x141091f70`, mode 7 of the state).
- Start (`AiStart` or `BrainStart`, both reach `GekkoAi::Start`): build the world, run the table initialisers (action table, AI state table, second layer, locomotion), build the creation context, start the nav controller if enabled, then `Begin` (Observer setup, which creates the ActionController, and the locomotion init `0x140f8ac40`), then Request(29 idle), InitInstance (which first runs an ActionController update), Dispatch(1), AI state 12. The locomotion state is idle (1) from its own init.
- Spawn chain: `TypeRegister`, then `TypeCreate` or `TypePlace`; `GekkoFull::Spawn` creates the full controller.

## 4. What is substituted

Places where the port answers a Survive engine call itself instead of running Survive's code or calling a TPP service. Each entry is a stand-in with an open item to remove it. The gekko runs without a Survive host, so the NPC service that Survive's registry would create is built by the host (`Build()` in `GekkoWorld.cpp`). Creating the real `SsdNpc` through Survive's registry is a current WIP.

### 4.1 Host NPC service (svc)

`svc` is the interface the plugin and the handlers call (the `SsdNpc` instance plus 0x20 in Survive). `Build()` fills these offsets with host objects:
- State table svc+0xf8: entries at +8 (0x28 bytes each) and a count at +0x10; the handlers call slot +0x10 `SetState(id, state, flag)`. The slots are logging traps.
- Pose object svc+0x48: pose scale table at +0x20 (16-byte entries, a float at +0xc), unit word table +0x28 (a word per unit id, 0 for unit 0), alive bitmap +8, frame time pointer +0x38 and a time scale +0x48 of 1.0. The frame time comes from the host because TPP drives the tick.
- Event bus svc+0x108: slot +0x88 (id, hash, data), used by the handlers at `0x140f936ae`. It is a logging trap, so effect and sound events are logged and not played.
- NPC list svc+0x10 (null), count svc+0x14 (1) and capacity svc+0x18 (1). The Observer setup sizes its per-instance arrays by the capacity.
- Nav service svc+0x60 (4.2).
- Owner lookup svc+0x68: slot +0x68 returns a pointer to an owner entry (a table of 0x1c byte entries); the entry leads to the object whose +0x10 is the component container the Observer setup queries.
- Target provider svc+0x70 (4.3).
- Route end report svc+0x78 (4.3).
- ActionController svc+0x80: Survive's own object (5.10), created by the Observer setup through svc slot 126 (+0x3f0, the function `0x141072c50`); [svc+0x30] is 0 and [svc+0x38] null so its update takes the all-units branch; [svc+0x50] (the action list component) is null because its creation `0x141073e00` returns at once while the replication bit of [svc+0x1fc] is clear.
- Fields that are still null are filled with trap objects. A read through one logs a single `[trap]` line. This is a diagnostic and gives no value.

### 5.1 Events and clip bits

Event keys come from the `.enchnk` of each gani; time is a fraction of the clip in units of 1/65535. Event `0xb9817d52` (a point event at 13101 of 65535 in slot 3) sets 0x200; `0x3903ca38` (a range event) sets 0x100. The mapper `0x140f81220` writes them into entry +0x110, and plugin frame kind 0 (`0x140f7ee21` to `0x140f7eee5`) clears the entry every frame; it runs through `GekkoPush::RunKind(0)` after the brain. The walk state runs the arrival test `0x140f88780` only while a bit is set: 0x200 picks stop clip slot 5, 0x100 slot 4. If the plugin frame does not run, nothing clears the bits and the loop clip never restarts. Event flags at record +0x288 are one-frame triggers cleared at the end of every kind-1 dispatch (for example `0x425b406c` sets 1, `0x68fa755c` sets 2).

Arrival: order type 2 is within radius 3.0 or passed, type 1 is the remaining path length, type 0 is at once. A 12 m walk headless stops at 2.25 m with slot 4.

Motion timing: TPP applies a requested motion when its stages run, Survive's controller when the call returns. A query right after `SetMotion` sees the previous clip (a turn was cut off after 33 ms). The finished answer is 0 until the controller has run once after the request (`NotifyControllerRan`, `g_motionAt`, `g_ctlRuns`) and the real query has answered 0 once for the new clip (4.7). Cause of the stuck turns (clips 33 and 34, 88 and 124 frames, 02:30 run) is read from code, not measured: SetMotion `0x140b6e920` only queues the request, the query `0x140af2110` (twin of Survive `0x140bc3210`, tail `0x141a7e570` vs `0x1419a2d30`, identical) reads the end bit of the current node record, which still belongs to the previous clip (normally ended) until the new node is written. In the 20:16 log every turn (clips 31, 33, 36) finished after its clip length (1.51, 1.48, 2.08 s), so the case did not recur.

### 5.4 Movement, navigation and routes

Route walk:
- In mode 0 with a route id at order +0xb0 the movement brain gets the route from `[[ctx+8]+0xa8]` (generation slot 1 against +0xac, `GetRoute` slot 0 into the per-unit cache at M+0x70), takes vertex `[+0xb4]` (group slot 1 count, slot 2 position), increments the vertex and requests a path (mode 1). After the last vertex it reports the end through `[svc+0x78]` vtable +0x60 (id, `0xbf169f98`, `0xffff`).
- A route walk has no target. Strength above 0 (`0x140fa477b`) enables the re-plan on a moving target, which otherwise jumps to the next vertex every 1.5 s.
- Each vertex is one move order with the 3.0 m arrival test, so the gekko stops at every vertex, as Survive does. Fewer stops need more waypoints per leg.
- The route system calls at `0x140fa4cde` (+0x00) and `0x140fa4cba` (+8) belong to `[[ctx+8]+0xa8]`, not to the nav object. TPP's `RouteSystemImpl` is wired there.

Nav service calls the movement brain makes on N (the object at `[svc+0x60]`, edx = unit id):
- Slot +0x00 (`0x140fa4eb6`): request a path. r8 points at start vec4 (own position) and goal vec4 at +0x10. Returns a path handle word stored at order record +0xb6. The brain builds the whole request itself (`0x140fa4e01` to `0x140fa4eb6`): +0 start, +0x10 goal, +0x70 token `0x40eca04e7699`, +0x78 = 1, floats at +0x84, +0x88, +0x8c, +0x90 bit 0 cleared.
- Slot +0x08 (`0x140fa4dc4`): release the old handle, then record +0xb6 = 0xffff.
- Slot +0x18 (`0x140fa4ef8`, `0x140fa5ac9`): returns a path record R (R+0 object A, R+8 handle).
- Slot +0x40 (`0x140fa4df6`, `0x140fa5792`): snap a point to the nav mesh (out vec4, in vec4, radius in xmm3, word `[rsp+0x20]` = 0xffff).
- Slot +0xa0 on A (`0x140fa4f82`, `0x140fa5b08`): path progress: dword +0 segment index, +4 fraction.
- Order record fields: +0x20 target vec4, +0x70 own position, +0x80 offset, +0x90 distance, +0xb0 mode hash, +0xb6 handle, +0xb8 mode byte.

### 5.5 Jumping and climbing

What Survive does:
- Survive's gekko has two jump actions: action 8 (leap) and action 9 (low hop). Both play slots 51 (take-off, 35 frames), 52 (air, 27 frames) and 53 (landing, 93 frames) and are ballistic: the handler computes a launch velocity at enter and integrates it.
- Survive does not jump over obstacles. Every request is tactical: retreat hop, gap-closing leap, flank hop, hop at a target outside a vertical band, and a ground-surface trigger. Nothing measures an obstacle's height or the room on top of it.
- The obstacle link: the blocked bit (5.4) or a Door segment puts the brain into mode 8 (action 30, a walk through) or mode 10 (hop through helper `0x140fa2af0`, needs bit 53, else action 31). Mode 10 is chosen when the target is more than 3.5 above the gekko, else mode 8. Conditions on both entries: a valid target id and a vector y with abs(y) <= 1.5 (`0x140fa5c7b`), and either strength > 0 or rec+0xa4 <= 0. Which vector the y test uses is not known.
- StepOn, StepDown, StepFence, LadderUp, LadderDown have no consumer in the gekko range `0x140f60000` to `0x140fb0000`. Actions 28 to 31 are not jumps.

Request format and inputs:
- Request (0xc0 bytes through the mailbox `0x140e96b60(controller, id, req)`): +0x10 vec4 target (w bits 0 to 2: 1 world position, 2 nav node), +0x20 action id, +0x24 flag byte. Flag 0x20 is the small variant, 0x04 the back-hop (aim away), 0x01 and 0x08 are for action 10. The handler record copies the vec to +0x210 and the flag to +0x2a3 (`0x140f936e0`).
- Brain inputs: order record +0x60 forward, +0x70 own position, +0x80 vector to target, +0x84 dy, +0x90 distance, +0xa0 vertical-band timer, +0xb8 mode, +0xbe and +0xbf one-shot flags. Rec+0xa0 grows by dt while strength > 0 and (dy > 3.0 or dy < -2.0), is reset to 0 otherwise when non-negative, and a request sets it to -7 - 2r.
- Target record T (`[M+0x68]`): +0x20 position, +0x30 id (-1 none), +0x34 strength, timers +0x38 to +0x60 (counting up while strength > 0, reset to -1, -5, -1, -10, -2, -5, -3, -12, -2 otherwise), +0x68 set to 1 after 2 s without a target. ### 5.6 Perception

What the gekko code does:
- The gekko code implements no sight or hearing. The Observer (`0x140f73a20`) hands its parameter blocks (5.7) to the SsdNpc object, which builds four generic perception components shared by all Survive NPCs. The gekko supplies one callback of its own, the notice listener, and the AI state chooser (`0x140f8d510`) never reads perception: it reads bits of the NPC state entry and the contact object (5.8).
- SsdNpc interface vtable `0x1422d21c0` (a second variant `0x1422d2900`); component factory is `0x141989050()` vtable slot 0, create(out, hash, args). Slots: +0x438 (`0x141073950`) sight aggregator `0x562d5ab8eadf` (npc+0x328 and +0xe8); +0x440 (`0x141073130`) sight parameter component `0x724c839dfd8d` (npc+0x330 and +0xf0); +0x448 (`0x1410733c0`) hearing `0x39119778cd06` (npc+0x2f0 and +0x90); +0x450 (`0x141073440`) notice `0x5b10d5d2e138` (npc+0x2f8 and +0x98, created with id `0x651a1306165b`).
- Sight forms (`0x14107f480`): the first 9 floats of the +0x8 block become 5 entries of 0x20 bytes {distance, hAngle * pi/180, vAngle * pi/180}; only these three triples feed the sight component.
- Sight parameter component (class vtable `0x1422d5328`, init `0x141089ad0`, update `0x14108a2c4`): reads the +0x8 block at offsets 0x28 to 0x54 and a second 12-float set at 0x5c to 0x88 enabled by the byte at +0x58, pushes each set to a client object with type byte 0x2a (base) or 0x27 (alternate), and reads the 12 camouflage floats into 0x30-byte rows. Gated by npc flag word `[npc+0x1fc]` bit 7.
- Hearing component (class vtable `0x1422d6ad8`, init `0x14108e750`, update `0x14108eb10`): squares the 10 hearing floats, multiplies by a global scale squared, and for every live NPC queries a noise source (object at base+0x60 = `[[0x141989050()+0xa8]+8]`, call `+8(query, out)` with query {vec4 position, word, dword cursor -1, word} returning a record pointer or 0, looped) and a per-NPC noise listener registration (`[[ctx+0x78]]` vtable +0x28, enabled when `[npc+0x1fc]` bit 2 is set). The range test is `0x14108e540`. Disabled when bit 1 or 7 of the flag word is set.
- Sight aggregator (class vtable `0x14236a448`, init `0x141799400`, update `0x141799ae0`): does no line test itself. It asks a hit provider `[[this+0x78]+8]` for count (+0x18, form, npc), record (+0x20, form, npc, index) and byte (+0x30), and creates typed per-NPC arrays through `[[ctx+0x88]]` vtable +8. The provider class and `[args+0x50]` are not found; the engine sight service is a Fox game service as in TPP (GsSightCheck, SightCheckDaemon). Results flow to the sight parameter component and to the sight event builder `0x141090370`.

Notice component (class vtable `0x1422d6dd8`, init `0x1410909d0`, update `0x1410913a0`, per-instance `0x141091460`, stride 0xa0 at base+0x58 as the interface sees it):
- Instance fields: byte +0x20 current level 0 to 13 (0xf none), dword +0x80 target id, +0x84 value, +0x68 pending noise record, +0x74 timer (1.0 s), +0x50 and +0x54 forget fields.
- Per instance and frame, in order: a reset flag (inst+0x99 bit 2) sets level 0xf; the hearing interface (npc+0x90 slot +8) returns a noise record, with the sound delay applied (`0x1410906a0`); sight events from npc+0xf0 (`0x141090370`: stage 3 gives type 0, stage 2 gives type 8, stage 1 gives type 8 when the category-1 notice counter is >= 3, else type 11; muted when state entry +0x10 bit 39 is set); listener slots +0x10 and +0x18 (stubs false for the gekko); the pending record goes to the listener's slot +8 (`0x1410902b0`, skipped when the record's id equals the unit's own composite id); the result passes to the gate `0x14108fb50`; then `0x141091680` publishes to a sink at base+0xb0 (class not found).
- Gate `0x14108fb50`: the target object comes from the target provider `[npc+0x70]` vtable +0x70(id). A position event is accepted only when the squared distance to the NPC is in 49 to 225 (7 m to 15 m) and a facing test passes (rotated offset result <= 0.5). The reject filters are listener slots +0x28 and +0x30 (`0x141141270` then `0x140fa7020`).
- Notice ladder: an event type is the level. Accepted transitions: L0: 0, 1, 8 to 13. L1: 0, 1, 4, 5, 6, 10. L2: 0, 1, 2, 8 to 13. L3: type <= 3. L4: 0 to 4, 8 to 13. L5: 0 to 5, 8 to 13. L6: 0 to 6. L7: 0 to 7. L8: 0 to 8. L9: type <= 9. L10: 0 to 10. L11: 0 to 11. L12: 0 to 12. L13: 0 to 13. When bit 2 of the target object byte +0x18 is set, L6 accepts 0 to 4 and 6, L7 accepts 0 to 8, L10 accepts 0 to 11, L11 accepts 0 to 11 and 13. Types 14 and up are rejected. When the level is 0xf the comparison level is inst+0x84. Extra rejects: state entry +0x10 bit 62 set, and npc+0x68 table entry (stride 0x1c) +0x18 == 1.

- Sound delay: a record with kind byte > 0x37 whose distance exceeds hearing float index 5 is held for distance * 0.00294118 s (1/340); a stronger record replaces the held one.
- Public interface (base+0x20, vtable `0x1422d6e10`): slot 0 `0x14108fb50` HandleNotice, 1 `0x141090170` refresh, 2 `0x141090920` get active event, 3 `0x1410908d0` get pending record, 4 `0x1410912a0` set inst+0x84, 6 `0x141090820` set inst+0x84 = 0xf, 9 `0x141090fc0` reset, 16 `0x141090f30` set timer, 22 to 25 per-category counters (9 categories, capped at 10; 23 increments, 24 clears one, 25 clears all, 22 reads).

### 5.7 Health, the parameter block and where the data comes from

Parameter struct `SsdGeckoParameter`: singleton pointer `[0x14307a8d0]`, create `0x140b98340` (allocates 0x1a8 bytes, ctor `0x140b980e0` then loader `0x140b983f0`), descriptor `0xdc11dba59fbb` registered under key `0xbf304b9d` (StrCode32 "Gecko") by `0x140b935d0`. The size is at least 0x198 (`kStructMin`). `GekkoParam::Fill` writes 86 entries (kind 0 f32, 1 u32, 2 u16, 3 u8):
- +0x08 sight: contact, normal, far sight forms (3 floats each: distance, horizontal angle, vertical angle). +0x2c, +0x60, +0x94: the base, dungeon and no-fog sight blocks of 0x34 bytes (reader `0x140c166b0`, sub-block reader `0x140c16a30`), one presence flag byte per block.
- +0xc8 sight camouflage (reader `0x140c15ff0`): four groups of three floats (enemy, character, object).
- +0xf8 hearing ranges (reader `0x140c15a50`): ten floats (zero, ss, hs, s, m, l, hll, ll, alert, special).
- +0x120 life (dword), +0x124 defense (dword, copied to every unit record +0x16), +0x14c expPointRateByFulton (0 becomes 150).
- +0x128 partsLife rightLeg, +0x12a leftLeg, +0x12c rightW, +0x12e leftW, +0x130 camera (words). +0x138 defense_weak, +0x13a defense_Leg, +0x13c defense_Gun, +0x13e defense_Locket, +0x148 bullet_defense (words).
- +0x150 four level bytes and +0x154 a 4 by 4 dword table of buff codes (buff_normal list, loader `0x140b985f0`). +0x194 coop_exp (0 becomes 100, loader `0x140b98760`).
- The loader reads `root["Gecko"]["baseParam"]` (first array element only, so there is no level index), `buff_normal` (up to 4 entries `{level, buffCode}`) and `coop_exp`. If `root["Gecko"]` is absent the loader returns at `0x140b9842c` and the struct keeps constructor state: every field 0 except +0x194 = 100. There is no fallback to another type. The only Zombie link is the level table row root (type key table at `0x1421f2890` maps Gecko to "Zombie").
- Sight ranges and sight form values in the block matter for perception (5.6): the values the port writes are the community capture's (below), for example baseSight discovery 15 m, normalSightForm 50 m, hearing ss 4.5, hs 5.5, s 9, m 15, l 30, ll 80.

Where the data comes from:
- The numbers are not in the shipped game files. Survive loads `SsdNpcLevelParameters` through the stored parameter system: Lua `StoredParameterSystem.StoreInit` (`0x140a6e1a0`; called from `init_sequence.lua` with `TppDefine.PARAMETER_FILE_PATH` when `PERSONAL_DATA` does not exist) opens each `.param` by path, decrypts it (`0x140069320`) and stores the blob under StrCode32(name) in a 0x50-byte entry table. The boot phase `0x140a51010` fetches the JSON root for id `0x91c0213b` (StrCode32 "SsdNpcLevelParameters") through slot +0x48 (`0x140a6ca10`: Blowfish key `0x1421f88c0`, zlib, JSON parse `0x140591c80`) and calls the 23 per-type loaders (the Gecko one through wrapper `0x140b98930`). The shipped copy under `server/parameter/SsdNpcLevelParameters.param` has no Gecko key. The path string at `0x1421f1890` (`.../chara/ssdnpc/levelParam/SsdNpcLevelParameters.json`) misses in every archive (160 variants tried), so the root in `0x140a53210` is null and the singletons stay at constructor defaults.
- A live server could replace a stored blob (strings `CMD_SERVER_PARAMETER_LOAD`, `CMD_SERVER_PARAMETER_GET_URL_LIST`); the response consumer is not traced. The store is saved in the personal save (`PERSONAL_DATA`, 4,197,392 bytes, cipher not found), which may hold a Gecko key; not checked.
- The port's block comes from the community server capture: `alicealys/mgv-server-emulator`, commit `defe443cba93b2f2ee0dcc19ddbb142b0d610bba`, file `src/server/resources/data/parameter/SsdNpcLevelParameters.json` (credit in the README). The capture's provenance is not known; its keys match the exe's loader (80 loader keys equal 80 JSON keys). `tools/gen_gekko_params.py` regenerates `GekkoParamBlock.h` and fails when the keys differ.
- Survive can also take a JSON text at run time: Lua module `SsdGecko` has `ReloadParameterTables` (table row `0x14223ab08`, function `0x140b988f0`) which parses the text with the reader (`0x140c15e80` vtable +0x48, text kept at singleton+0x1a0) and runs the Gecko loader in place. Fourteen modules have this function. Only the Lua VM calls it.
- The JSON tree is JsonCpp compiled into the exe (`0x141927000` to `0x141931000`, no vtables): `Reader::parse` `0x14192e0e0`, Value ctor `0x141929870`, `operator[]` `0x141929f10` (stub to `0x14192b3c0`), find `0x14192a020`, begin `0x14192a660`, deref `0x14192a6f0`, null test `0x14192b0a0`, typed getters `0x140591a60` (int), `0x140591800` (bool), `0x1405918a0` (float), file load `0x140591af0`, parse `0x140591c80` (pass key 0, with a key it requires root[key] to be a non-null object). The closure of the library is 79 functions (22,798 bytes) plus 23 external callees (allocator wrappers `0x140001290`, `0x1400012a0`, CRT helpers). It is small and has no engine globals except the null value `0x1430b9590`. Lifting it would let Survive's own loader run on a JSON text (the option that replaces the native write).

### 5.8 Hits and damage

Reception (TPP side, `GekkoHit.cpp`):
- Native hit targets have a callback interface at object +0x30 (callback +0x78 empty for types 15, 45, 50 and 63; types 76 to 91 at +0x78). `fox::geo::TargetSweepCheck::Hit` calls interface slot 1 (+8) as a filter (self, A+0x18, B+0x18, GeoResult, user) and drops the hit when it returns 0. ### 5.9 Pause and time

`GameTime::Update` forces dt 0 while the pause mask is set. `GekkoFull::ConsumeRunTime` reads the engine's run flag and returns 0 while paused. The execution skip bitmap is at context +0x10; a bit equal to the context flag means run. A `Sahelan2` instance does per frame: run or skip from the bitmap, then `ExecutePlugin` and the controller stages in order; the gekko follows the same structure.

### 5.10 AI states and actions

ActionController (how Survive controls the gekko; lifted since 07/10/2026):
- What it is. The controller is the generic NPC class created through the NPC service slot 126 (+0x3f0). It is an object of 0xc0 bytes with an interface sub-object at +0x20 (vtable `0x14228aaa0`, 19 slots); the pointer every consumer keeps ([svc+0x80], [H+0x1c8], [L+0x88]) is the interface. Setup (`0x140e794e0`) caches the NPC service, the nav service, looks up two small gekko components by key (their interfaces go to +0x90 and +0x98) and allocates, per unit, a request array entry of 0xc0 bytes (+0x28) and a record of 0x1d0 bytes (+0x30). - Who writes requests. The AI state handlers (one request per action, category 0, kind 4) and the movement brain (move orders, kind 1) fill a 0xc0 byte record on their stack and call the mailbox `0x140e96b60(controller, unit id, request)`. A request has the target at +0x10, the action at +0x20, the flag byte at +0x24, the goal position at +0x90, the order bits at +0xb8 (bits 3 to 5 are the category) and the kind at +0xb9. The mailbox only copies it into the unit's record at +0x20 (into the queue at +0xe0 while record flag 0x400 is set) and sets flag 0x200.
- How it is chosen and entered. The update (interface slot 9, `0x140e7a0f0`) visits every unit once a frame. For a record with flag 0x200 it clears the flag and runs the commit (slot 15, `0x140e78390`). The commit reads the category from bits 3 to 5 of the order byte. Category 0, a plain action: it builds the request array entry from the request (fields +0x10 to +0xa0 copied, kind +0xb9 becomes entry byte +0xb6, +0xba becomes +0xb7, order type bits 0), converts the look bits (slot 14, `0x140e79f20`) and stores it (slot 13, `0x140e79e00`), which writes the entry, increments the serial in word +0xae and sets record flag 0x10. Category 1: the same, but the entry gets order type 2 (a position order to the goal at +0x90). Categories 2 to 4: the record flags get 0x02 (path pending) and nothing else happens for a unit this machine owns, unless the category is 4; a unit that another machine owns would ask the nav service for a path here. The Realized dispatch (`0x140f936e0`) then takes entries with byte +0xb6 equal to 4 and copies the action into the unit's action record, and the locomotion reads entries with byte +0xb6 equal to 1.
- How the order is built. For the movement brain's normal move order (category 2) the brain has already asked the nav service for a path itself and keeps the handle in its order record (+0xb6). Each update, per unit, `0x140e7a4e0` does the bookkeeping: if the consumer took the entry (word +0xb4 bit 4) and the record is accepted (0x08) it sets finished (0x20), which is what the AI states wait for; otherwise, while the record is path pending, it asks the nav service for the unit's navigator record, asks whether the result for the latest request has arrived (the result counter equals the request counter; the controller sets it when it receives the pathfinder result) and calls the gekko component's step (`0x140f76a20`). That step needs the path; it takes the point count, copies the record's request into a new entry, sets order type 1 (path) and +0xac to the count minus one (the last point), converts the look bits, stores it through slot 13 and sets record flag 0x08. The path is not stored in the order: the locomotion record +0x20 holds the unit's navigator record (set once by the locomotion init `0x140f8ac40`), and the arrival test and the heading read the path through it. As long as the path is current the step runs every frame, so the order is level triggered and a replaced path is picked up at once.
- How the order type is used. The locomotion reads word +0xb4 of the entry and keeps its low two bits: 0 means arrived at once (the idle state never starts a walk), 1 follows the path (heading for the next path point, `0x140f88cc0` branch 1; arrival is the remaining path length up to +0xac), 2 walks straight at the goal at +0x90. So a position order that ends in order type 1 is how Survive makes the gekko walk around obstacles: the nav path decides, the brain's blocked ray only matters for doors and hops (modes 8 and 10).
- How the heading request reaches the body. Survive's locomotion writes the target orientation (+0x80), the flag 0x100 (+0x190) and N (+0x1a8) into the controller's motion output, which is the CharaControl interface; the CharaControl keeps turning toward the target by 1 - pow(1 - 1/N, ticks * 0.2) per frame for as long as the flag is set (`0x1419f22dc`, and TPP's twin), and copies its rotation into the target while the flag is clear. The flag is persistent in both games. The walk state clears it on enter (`0x140f8a157`); an order whose locomotion record byte +0x46 is 1 (set from request dword +0x18, which is the brain's direct move order) sets it again on enter with N 30, and every other walk sets it in each frame of its update with N 90; the stop and idle states leave it alone (their late event only ORs bits 0 and 1 into +0x190); the turn state (4) clears it in its move step (mode 7, `0x140f89260`), which the base ticks never call: the engine calls the locomotion's move step (slot 20, `0x141091f70`) every frame. The port now calls it (`GekkoWorld::MoveStep`). Result of a headless run (start push simhas=0 route=3 sim=1500 with the nav controller): the request is set in 344 walk frames and stays set in 1061 idle or stop frames, in which the body turns 0.010 rad in total, because the target is the last walk heading and the walk has caught up with it. With the straight-line stand-in nav and 6000 frames the same count is 1539 frames and 0.516 rad: the body is still turning toward the last heading when the unit stops, by the same persistence, slowly (N 90).
